# M365-Secure

M365-Secure is a Rust CLI, `m365-assess`, that assesses the security configuration of a Microsoft 365 tenant. It signs in once, reads configuration from Microsoft Graph and the other admin APIs it can reach, checks each setting against a control registry, and writes HTML, CSV and JSON reports. Every finding carries CIS Microsoft 365 (v6 and v7), NIST CSF 2.0, NIST SP 800-53, Essential Eight and other framework references. Source: [jusso-dev/M365-Secure](https://github.com/jusso-dev/M365-Secure).

`Cargo.toml` declares the MIT licence, but the repository has no LICENSE file yet.

## When to Use

- The user wants to assess a Microsoft 365 tenant they are authorised to assess, or re-render an earlier report.
- The user asks what a check id, status or framework mapping in an M365-Secure report means.
- The user wants to add or change checks, modules or registry entries.
- Not for changing tenant settings. The tool only reads.

## Run an assessment

Only run against a tenant the user owns or has written authority to assess. Confirm that before signing in.

```bash
cargo build --release                       # target/release/m365-assess
export M365_TENANT_ID="<tenant-guid>"
m365-assess auth login                      # device code; prints a code and URL
m365-assess scan list
m365-assess scan full
m365-assess scan full --include inventory,soc2,powerbi,value
m365-assess scan module identity
m365-assess report generate --input M365-Assessment/_Assessment-Results_<domain>.json --output ./rerendered --format html,csv,json
m365-assess info                            # version, frameworks, Graph scopes
m365-assess auth status
m365-assess auth logout
```

- Without `--client-id` it uses a Microsoft first-party client, which covers Graph and Exchange Online only. For Azure, SharePoint admin, Teams admin, Defender for Endpoint and Power Platform checks, the tenant needs its own app registration with those API permissions, passed with `--client-id` or `M365_CLIENT_ID`.
- Client credentials (`auth login --client-secret`) suit automation. Keep the secret in the environment or a secret store. Never paste it into chat or a file in the repo.
- `--cloud commercial|gcchigh|dod` selects the cloud.
- Default modules: `identity`, `licensing`, `exchange`, `security`, `collaboration`, `intune`, `hybrid`, `azure`. Opt-in: `powerbi`, `purview`, `inventory`, `soc2`, `value`.
- Azure, Defender for Endpoint and Power Platform calls go through [Junction](https://github.com/jusso-dev/junction) under a read-only policy.

## Read the results

| Status | Meaning |
| --- | --- |
| `Pass` / `Fail` | Scored. Score is Pass / (Pass + Fail). |
| `Warning` | Partly met. Not scored. |
| `Review` | Evidence collected, a person must decide. Not scored. |
| `Info` | Inventory. Not scored. |
| `Unknown` | The check could not run (permission, consent, licence or API error). `current_value` gives the reason. Treat it as unassessed, never as a fail. |
| `NotLicensed` | The tenant lacks the needed service plan. |

When summarising, lead with High and Critical `Fail` findings, then list `Unknown` checks and what permission or consent would let them run. Do not round `Unknown` into a pass or a fail.

The JSON report (schema 1.1) can be imported into crownguard to pre-fill its Microsoft 365 questions.

## Developing

- `src/main.rs`, `src/cli.rs`: entry point and arguments.
- `src/auth/`: sign-in, token cache and the `Resource` token exchange. `GRAPH_SCOPES` lists delegated Graph scopes.
- `src/modules/`: one module per area (`identity`, `exchange`, `security`, `collaboration`, `intune`, `azure`, plus `hybrid.rs`, `licensing.rs`, `powerbi.rs`, `purview.rs`, `inventory.rs`, `soc2.rs`, `value_opportunity.rs`).
- `src/junction.rs`: the gateway to Junction operations. `controls/junction-operations.txt` lists the operations used and `controls/junction-catalog.json` embeds them. Regenerate with `scripts/junction-catalog.py /path/to/junction/checkout` after adding operations or bumping the pinned Junction revision in `Cargo.toml`.
- `controls/registry.json` and overlays in `controls/registry.d/`: every check id, collector, licensing and framework mapping. New checks go in an overlay. `risk-severity.json` and `licensing-overlay.json` adjust severity and licensing.
- `docs/CHECKS.md`: the full check list, generated by `scripts/checks-table.py`.
- Before a pull request (same as CI):

```bash
cargo fmt --all --check
cargo build --locked
cargo test --locked
cargo clippy --locked -- -D warnings
```

`tests/registry_consistency.rs` checks the registry against the code.

## Pitfalls

- The first build needs network access to fetch the pinned Junction crates.
- Adding a scope to `GRAPH_SCOPES` changes what admins must consent to. Call it out in the pull request.
- A new check must never silently disappear. If it cannot run, it reports `Unknown` with a reason.

## Safety rules

- Reports contain tenant names, domains and configuration. `M365-Assessment/`, `*.html`, `*.csv` and `*.pdf` are gitignored. Never commit report output, tokens or tenant ids.
- Use synthetic data in tests and fixtures.
- Do not share a client's report outside the conversation without the user's say-so.

## Verification

- For a scan: report the tool version, modules run, the score and counts by status.
- For code: fmt, build, test and clippy pass, and `docs/CHECKS.md` is regenerated when checks change.
